SER014
-

Batches and transactions on the context surface: `RespBatch`, `RespTransaction`, and the
`BeginBatch()` / `BeginTransaction()` extensions that start them.

```csharp
using var batch = db.BeginBatch();
var a = batch.Strings.GetAsync("a");
var b = batch.Hashes.LengthAsync("h");
await batch.ExecuteAsync();          // explicit: nothing is sent until this
Console.WriteLine($"{await a} {await b}");

using var tran = db.BeginTransaction();
var check = tran.AddCondition(Condition.KeyNotExists("lock"));
_ = tran.Strings.SetAsync("lock", "me");
bool ran = await tran.ExecuteAsync(); // false if a condition failed or a watched key changed
```

Both are `IRespKeyspaceTarget`s, so every keyspace group (`Strings`, `Hashes`, ...) is reached exactly as it
is on a database, through the same constrained generic extensions - the batch is a struct and is not boxed.

Settled enough to build on:

- execution is **explicit**. A command that throws while a batch is being composed must not cause the
  half-built batch to be sent, so leaving a `using` scope *discards* rather than executes, faulting the
  tasks of anything queued
- `ExecuteAsync` returns something: on a transaction, whether it ran
- `Begin...` rather than `Create...`, because `IDatabase.CreateBatch()` is an instance member and would
  always win

Not settled, and the reason this is gated:

- conditions use the shipped `Condition` type. They are rare, so they are borrowed rather than redesigned;
  a context-surface spelling may replace them
- whether a batch's `ExecuteAsync` should complete on *written* (today) or on *answered*
- whether these stay structs; a copy shares the queue, so executing or discarding any copy affects all
