# Maintenance notifications - SER010 retired

**This diagnostic is no longer produced.** Server-native maintenance notifications ("smart client
handoffs") are no longer marked `[Experimental]`, so nothing emits `SER010` and no suppression is needed.
The page is kept because the diagnostic's help link pointed here, and older builds still carry it.

If you have a suppression for `SER010` - in a `csproj`, a `.editorconfig`, or a `#pragma` - it is now
inert, and can be removed whenever it suits you.

For how the feature works and how to configure it, see [ServerMaintenanceEvent](../ServerMaintenanceEvent.md).

## What it covered

Maintenance notifications are a server feature by which a server warns a connected client in advance of
a disruptive event - a shard migration, a failover, or the endpoint itself being replaced - so the client
can act before the disruption rather than react to a broken connection afterwards. The gated surface was:

- the `MaintenanceNotificationMode` and `MaintenanceEndpointType` enums, and the
  `MaintenanceNotifications`, `MaintenanceMovingEndpointType`, `MaintenanceRelaxedTimeout`,
  `MaintenanceRelaxedWindowMax` and `MaintenancePostEventRelaxedDuration` options on
  `ConfigurationOptions` and `DefaultOptionsProvider`
- `PushMaintenanceEvent`, `ClusterSlotMigration` and `MaintenanceNotificationType`
- the `MaintenanceType` property on `FaultContext`, `RedisConnectionException` and `RedisTimeoutException`

## What it used to mean

While the feature was experimental, it was flagged as subject to change for three reasons:

1. **The server side is not universal.** Only Redis Enterprise and Redis Cloud emitted these
   notifications; OSS Redis, Valkey and Garnet do not recognize the opt-in at all.
2. **The wire contract was still evolving.** Notification types were proposed and withdrawn during its
   development, and the payloads are described in prose rather than by a formal specification.
3. **What the client *does* in response was being built in stages** - timeout relaxation, then endpoint
   handoff - so behaviour could change materially between versions even where the API did not.

Acknowledging that was what the suppression meant:

```xml
<NoWarn>$(NoWarn);SER010</NoWarn>
```

or more granularly / locally in C#:

``` c#
#pragma warning disable SER010
```

## Reserved, not recycled

`SER010` is not reused for anything else, so an old suppression cannot silently hide an unrelated
warning. The same applies to the other retired identifiers - see `Experiments.cs`.
