Failback health checks let a group ask, before moving traffic *to* a member, whether that member is fit to
take it: typically, in an Active-Active deployment, whether it has caught up with the others, rather than
only whether it is alive. See [Failback health checks](../Failover.md#failback-health-checks) for the rules.

The diagnostic covers:

- `ConnectionGroupMember.FailbackHealthCheck` and `MultiGroupOptions.FailbackHealthCheck` (and its builder);
- `HealthCheckProbe.Scope` and `HealthCheckProbeScope`, for probes that answer per member rather than per
  endpoint.

It is experimental for two reasons:

1. **The selection rules are new and deliberately differ from other clients.** A failback check never evicts
   the active member, and when no live member passes it, selection falls back to liveness rather than refusing
   to serve. Both choices follow from measurements against real Active-Active deployments, where a partition
   between regions leaves every member behind at once; they may still be refined.
2. **The probe it was built for is still to come.** The intended use is Redis Enterprise's lag-aware
   availability API, through a probe that has not shipped yet. Until it has, and has been exercised against
   real deployments, the shape of this API may change.

If you accept the above, you can suppress this warning by adding the following to your `csproj` file:

```xml
<NoWarn>$(NoWarn);SER011</NoWarn>
```

or more granularly / locally in C#:

``` c#
#pragma warning disable SER011
```
