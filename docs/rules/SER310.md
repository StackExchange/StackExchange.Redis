# SER310: this redis call cannot honour the cancellation token in scope

The method accepts a `CancellationToken`, and calls a redis API that cannot act on one. The token is
silently ignored: cancel it, and the call keeps waiting for the server exactly as before.

```c#
// flagged - the signature promises cancellation, the call cannot deliver it
public async Task<string?> GetAsync(IDatabase db, string key, CancellationToken cancellationToken)
    => await db.StringGetAsync(key);

// suggested - the context surface accepts the token
public async Task<string?> GetAsync(IDatabase db, string key, CancellationToken cancellationToken)
    => await db.Context.Strings.GetAsync(key, cancellationToken: cancellationToken);
```

## Why this is a suggestion and not a warning

There is nothing wrong with the code. Plenty of methods take a token because their *callers* do, and have
no particular need to act on it; flagging those as defects would be wrong, and a rule that cries wolf gets
turned off.

What it is worth pointing out is the mismatch. A method signature that accepts a `CancellationToken` is a
promise to the caller, and this is a place where the promise cannot be kept - which is invisible in the
source, and shows up only as a request that carries on after everything else has stopped.

## Why the old API cannot simply be fixed

The classic surface sends through a pipeline that has no way to withdraw a request once it has reached the
socket, and no way to say "ignore the reply that is coming" without desynchronising every reply after it.
Honouring the token there would mean abandoning the caller while the command still runs on the server -
which is not cancellation, it is a lie about cancellation, and a worse one than saying nothing.

The newer RESP context surface is built on an operation that owns its own completion, so a token can
genuinely take the outcome first: the registration is taken when the request is attached and released the
moment any definite outcome is reached, and a cancellation competes for the same single-winner claim that
a reply does. Exactly one of them wins.

## Suppressing it

If a method takes a token for its callers' sake and this call is deliberately not cancellable:

```c#
#pragma warning disable SER310 // this call is not cancellable; the token is for the caller's benefit
```

or turn it off for a project in `.editorconfig`:

```ini
dotnet_diagnostic.SER310.severity = none
```
